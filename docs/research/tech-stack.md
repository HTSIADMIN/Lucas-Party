# Realtime tech-stack research: Jackbox-style party platform

Researched 2026-10-31 via web search and page fetches. Tags: **[official]** = vendor/project docs I fetched; **[community]** = third-party code, reverse engineering or blogs; **[vendor]** = source sells a competing product; **[est]** = my arithmetic or judgment; **[unverified]** = could not confirm. Text is paraphrased; only a few short labels are quoted.

## 0. Key takeaways

1. **Language is not the bottleneck.** Node `ws` on one core did about 45,000 ping-pong round trips/s (median 21.7 us) in an Oct 2026 loopback test ([Lemire](https://lemire.me/blog/2026/10/10/websocket-servers-in-javascript-node-js-bun-and-deno-in-2026/)). Supabase Realtime (itself Elixir/Phoenix, [repo](https://github.com/supabase/realtime)) reports Broadcast median 6 ms at 32,000 users ([benchmarks](https://supabase.com/docs/guides/realtime/benchmarks)). An 8-player room is about 9 sockets. "Feels slow" most likely comes from HTTP polling plus serverless/DB round trips **[est]**.
2. **Every phone-controller platform I could inspect relays through servers over WebSocket-style transports** (Jackbox, Kahoot, skribbl.io, Gartic Phone, Discord Activities). AirConsole is the only one documented to also use WebRTC, and only where browsers support it.
3. **Vercel can now hold WebSockets** (public beta 2026-06-22, GA changelog dated 2026-10-20, all plans) but every connection is cut at the function's max duration (Hobby 300 s, Pro 800 s), is pinned to one instance, and gets no room affinity. Room state must still live in Redis/DB.
4. **PartyKit's hosted platform is gone**: deploys stopped 2026-10-16, platform shut down 2026-10-23. Successor PartyServer runs in your own Cloudflare account ([migration guide](https://docs.partykit.io/guides/migrate-to-partyserver/)).
5. **Supabase Realtime Free is too small for live-ticking rooms**: 200 connections, 100 msgs/s, 2M msgs/month; Broadcast is billed per recipient.
6. **`node:sqlite` is Stability 1.2 (release candidate) on Node 24.15+ and Node 26, no flag needed**, but classes were renamed in v26.11, so the API is not frozen.
7. Cheapest always-on boxes: Fly shared-cpu-1x 256 MB $2.19/mo, DigitalOcean $4/mo, Hetzner from EUR 5.49/mo, Render Starter $7/mo.

## 2. Room-based realtime server options

### 2.1 Libraries you self-host

| Option | What it is | Key facts |
|---|---|---|
| **Node `ws`** | Plain WebSocket lib; rooms are just a `Map` you write | Passes Autobahn; permessage-deflate is off by default on the server and the README warns it can fragment memory under load; no benchmark claims ([README](https://github.com/websockets/ws)). Not natively compatible with Socket.IO clients. |
| **uWebSockets.js** | C++ addon, fastest Node option | Not on npm (install from GitHub); claims 20x Socket.IO; Apache-2.0 but README asks forks to rename and reserves other IP rights ([README](https://github.com/uNetworking/uWebSockets.js)). Idle connection ~5 KB, but ~9 s to absorb a 20k reconnect storm ([Evil Martians](https://evilmartians.com/chronicles/choose-your-fighter-benchmarking-5-websocket-servers-for-nodejs)). |
| **Socket.IO 4.x** | Own protocol on top of Engine.IO (not plain WebSocket): reconnect, rooms, acks, long-poll fallback ([docs](https://socket.io/docs/v4/)) | ~52 KB per idle connection and a ~120k connection ceiling per node in one test ([Evil Martians](https://evilmartians.com/chronicles/choose-your-fighter-benchmarking-5-websocket-servers-for-nodejs)). Multi-node needs sticky sessions or WebSocket-only transport, plus an adapter ([docs](https://socket.io/docs/v4/using-multiple-nodes/)). Connection State Recovery replays missed packets after short drops (example: 2 min; not supported by the Redis adapter) ([docs](https://socket.io/docs/v4/connection-state-recovery)). |
| **Colyseus 0.18** | Node room framework: matchmaking, binary delta state sync, reconnection; transports WebSocket (default), uWS, WebTransport, Bun ([docs](https://docs.colyseus.io/)) | Open source is free; Colyseus Cloud from $15/mo with no CCU limits ([pricing](https://www.colyseus.io/pricing)). Fast-moving: the landing page now announces 0.18; an earlier docs snapshot said 0.17 supported only the TypeScript SDK ([snapshot](https://docs.colyseus.io/examples), seen via search only **[unverified]**), so pin versions. |
| **Go** | `coder/websocket` (formerly nhooyr, maintained by Coder since 2024; passes Autobahn) ([repo](https://github.com/coder/websocket)) | Fine, no reason to pick it over Node here **[est]**. |
| **Rust** | axum 0.8.9 `WebSocketUpgrade`; tokio-tungstenite underneath ([docs.rs](https://docs.rs/axum/latest/axum/extract/ws/index.html)) | The docs page shows splitting a socket into send/receive tasks and says nothing about broadcast, so expect to write the room hub yourself (e.g. tokio channels). |
| **Elixir / Phoenix 1.8** | Channels with topics, PubSub, Presence; delivery is at-most-once ([guide](https://phoenix.hexdocs.pm/channels.html)) | 2015 synthetic test: 2M idle WebSockets on one 40-core / 128 GB box ([Phoenix blog](https://phoenixframework.org/blog/the-road-to-2-million-websocket-connections)). New language for this project. |

### 2.2 Cloudflare Durable Objects / PartyServer
- One Durable Object per room is the documented pattern (chat room, game session); a DO handles roughly 500-1,000 simple requests/s, so a room is far below it ([rules](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/)). Soft limit 1,000 req/s per object; received WebSocket messages up to 32 MiB ([limits](https://developers.cloudflare.com/durable-objects/platform/limits/)).
- **Free plan covers it**: SQLite-backed DOs only, 100,000 requests/day, 13,000 GB-s/day, 5 GB storage; operations start failing once a daily cap is hit ([pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). Paid: $5/mo minimum, 1M requests + 400k GB-s included, then $0.15/M requests and $12.50/M GB-s.
- **Billing for WebSockets**: connecting = 1 request; incoming messages bill 20:1 (100 messages = 5 requests); outgoing messages free; duration billed at 128 MB; an idle DO that is eligible to hibernate is not billed for duration ([pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)).
- **Hibernation caveats**: in-memory state is reset when it wakes; alarms, `setTimeout`/`setInterval` and outbound sockets prevent hibernation; per-socket metadata limited to 16,384 bytes via `serializeAttachment`; a forced code update disconnects sockets ([WebSockets guide](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)). A ticking game timer therefore keeps the room awake and billed.
- **Free-plan capacity [est]**: 100k requests/day x 20 = about 2M incoming messages/day; 13,000 GB-s / 0.125 GB = 104,000 s, about 28.9 room-hours awake per day. Plenty for turn-based games; a many-room real-time night could hit it.
- **PartyKit**: hosted platform shut down 2026-10-23. **PartyServer** (ISC licence) keeps the model (rooms, `onConnect`/`onMessage`, hibernation via `static options = { hibernate: true }`, broadcast) as a plain Worker + DO deployed with `wrangler`; `partysocket` is the reconnecting client ([migration](https://docs.partykit.io/guides/migrate-to-partyserver/), [repo](https://github.com/cloudflare/partykit)).

### 2.3 Supabase Realtime
- Limits ([page](https://supabase.com/docs/guides/realtime/limits)): Free = 200 concurrent connections, 100 msgs/s, 100 joins/s, 256 KB broadcast payload, 20 presence msgs/s. Pro = 500 / 500 / 500, 3 MB payload. Pro without spend cap, Team = 10,000 connections, 2,500 msgs/s. Exceeding message rate disconnects clients (supabase-js reconnects) ([quotas](https://supabase.com/docs/guides/realtime/quotas)).
- Billing ([pricing](https://supabase.com/docs/guides/realtime/pricing)): 2M msgs/mo Free, 5M Pro; then $2.50 per million and $10 per 1,000 peak connections. A Broadcast counts as 1 sent + 1 per receiving client ([usage guide](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages)).
- No server-side game authority and no delivery guarantee ([repo README](https://github.com/supabase/realtime)).
- **Fit [est]**: 30 rooms x 9 sockets = 270 connections, over the Free 200 cap (within Pro 500). A crash room that pushes a multiplier at 20 Hz to 9 sockets is about 200 events/s, over Free's 100/s cap if the cap counts per recipient (docs do not say **[unverified]**) and about 3 hours of play per month against the 2M Free allowance. Sending a start time + curve once removes that load.

### 2.4 Vercel Functions WebSockets
- Status: beta started 2026-06-22 ([KB](https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections)); a "generally available" changelog is dated 2026-10-20 ([changelog](https://vercel.com/changelog/websocket-support-is-now-generally-available)); docs page last updated 2026-08-10 says all plans, requires Fluid compute ([docs](https://vercel.com/docs/functions/websockets)).
- Connection closes at max duration: Hobby 300 s; Pro 800 s (1,800 s extended beta) ([limits](https://vercel.com/docs/functions/limitations)). One connection is pinned to one instance; reconnects may land anywhere; after a deploy old sockets stay on the old deployment; rooms/presence/pub-sub must go through an external store such as Redis ([docs](https://vercel.com/docs/functions/websockets), [realtime guide](https://vercel.com/kb/guide/publish-and-subscribe-to-realtime-data-on-vercel)).
- Next.js has no native upgrade API; use `upgradeWebSocket()` from `@vercel/functions` 3.10+. Socket.IO must be forced to `transports: ['websocket']`.
- Cost: Active CPU only while processing messages, Provisioned Memory for the instance lifetime while any socket is open; Hobby includes 4 h Active CPU, 360 GB-h memory, 1M invocations ([pricing](https://vercel.com/docs/functions/usage-and-pricing)). Vercel's own guide recommends a managed realtime provider for high-volume client fan-out.
- **Implication [est]**: usable for turn-based phases with Redis fan-out, but a 30-60 min party means several forced reconnects per player on Hobby, and nothing keeps one room's players on one instance.

## 3. Relayed WebSocket vs WebRTC data channels

- WebSocket runs on TCP, so a delayed packet holds up everything behind it (head-of-line blocking). WebRTC data channels can be unordered and/or limited by `maxRetransmits` / `maxPacketLifeTime`, i.e. UDP-like ([Rune](https://developers.rune.ai/blog/webrtc-vs-websockets-for-multiplayer-games), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/RTCDataChannel)).
- WebRTC still needs a signalling channel (normally a WebSocket) and STUN/TURN. Twilio says STUN alone suffices about 85% of the time ([Twilio](https://twilio.com/en-us/stun-turn), **[vendor]**); Fora Soft says TURN fallback is typically 10-20% of production sessions ([glossary](https://www.forasoft.com/learn/video-streaming/glossary/terms-streaming/nat), **[vendor]**); a second consultancy's 15-25% (higher on carrier NAT) was seen only in a search snippet **[unverified]**. No independent measurement found. Cloudflare TURN: first 1,000 GB/mo free, then $0.05/GB; STUN free ([FAQ](https://developers.cloudflare.com/realtime/turn/faq/)).
- What the platforms do: AirConsole relays by default and adds WebRTC when supported ([FAQ](https://developers.airconsole.com/faq-help)); Jackbox and Kahoot use WebSocket relays (section 1); Discord Activities cannot use WebRTC at all ([docs](https://docs.discord.com/developers/activities/development-guides/networking)).
- WebTransport (datagrams over HTTP/3): Safari 26.4 on 2026-03-24 made it "Baseline newly available"; widely available projected 2028-09-24 ([feature page](https://web-platform-dx.github.io/web-features-explorer/features/webtransport)). Colyseus lists it as a transport option; Discord does not support it yet.
- No measured phone-to-TV latency comparison found for any platform **[unverified]**. My judgment **[est]**: for taps and cash-out presses at ~10-25 msgs/s, a same-region WebSocket relay is enough; head-of-line blocking only matters on lossy Wi-Fi and you can mitigate it by sending latest-state-wins messages. Server region versus players matters more than protocol.
- **Mobile gotcha [community]**: iOS Safari (and all iOS browsers, WebKit) can kill WebSockets on screen lock/background without firing `close`, because timers are throttled; fixes reported are reconnecting on `visibilitychange`/`pageshow`, app-level heartbeats and state resync ([Flarum issue](https://github.com/flarum/framework/issues/4588), [WebKit bug 247943](https://bugs.webkit.org/show_bug.cgi?id=247943), [Reflex PR](https://github.com/reflex-dev/reflex/pull/366)). Not verified as fixed in current iOS.

**Implications for 8-player rooms [est]:**
- 30 rooms x 9 sockets = 270 connections. Tap race at 10 taps/s per phone + 10 Hz state broadcast is about 170 msgs/s per room, about 5k msgs/s across 30 rooms; even at AirConsole's 25 msgs/s per-phone cap and 30 Hz broadcasts it is about 14k msgs/s.
- One `ws` core handled about 90k messages in + 90k out per second on loopback (45k round trips x 2 each way), so the worst case above is single-digit percent of that best-case ceiling before TLS, JSON and game logic. Run one process; shard by room code only if you ever outgrow it.
- Across Rust/Go/Bun/C++ the spread is about 1.3-1.4x (3300 vs 2500 vs 2400 at 1 vCPU), 2.6x vs Elixir, and all are thousands of streams per core: orders of magnitude above this load.
- Memory is irrelevant at this scale (270 sockets x 52 KB is about 14 MB even for Socket.IO).

## 7. Recommendation

**Do not rewrite in Rust.** Replace polling with persistent sockets; the language was never the constraint.

**Default plan for a hobby-scale party platform**
1. Keep Next.js on Vercel for pages, auth, shop and wallet; keep Supabase Postgres as system of record.
2. Add **one small always-on Node 24/26 TypeScript process using `ws`**: a `Map` of room code to authoritative state, JSON messages with sequence numbers, app-level heartbeat, per-seat resume token, TV and phones all just clients. One process means no sticky sessions, no pub/sub layer and a single network hop. Host it on Fly (512 MB shared-cpu, about $3.69/mo + a volume) or a $4-6 VPS; Render Starter ($7) is the no-ops fallback. Verify the existing signed session token on the WebSocket upgrade (or exchange it for a short-lived ticket) **[est]**.
3. Persist only what you must: results and wallet changes to Postgres at round end; optional room snapshots to SQLite (`node:sqlite` on 24.15+/26, or `better-sqlite3` 13.x) so a restart or deploy can restore rooms.
4. Design for the real risks: send events, not ticks (crash game: send start time and growth curve, validate cash-out on the server clock); throttle and coalesce input to at most 20-25 msgs/s per phone (AirConsole's own cap is 25); resume after mobile lock via `visibilitychange`/`pageshow` plus replay of missed events (what Socket.IO CSR and AirConsole do); place the server in the players' region.

**Alternatives**
- **Cloudflare PartyServer / Durable Objects**: best if you want zero servers to babysit and a room-per-actor model with hibernation and built-in SQLite. Budget the $5/mo plan if rooms run timers. Cost: a second runtime and codebase beside Next.js; deploys drop sockets.
- **Supabase Broadcast/Presence**: fine for low-rate turn-based lobbies (you already use it); not for 10-30 Hz loops on Free; needs Pro for more than ~200 connections.
- **Colyseus** if you want built-in schema state sync and rooms (self-host free); accept version churn.
- **Vercel WebSockets**: only with Redis fan-out and reconnect handling; weak fit for room affinity.
- **WebRTC**: skip unless you later need sub-30 ms, loss-tolerant input on LAN **[est]**.

**When Rust would actually pay off**
- CPU-bound simulation per room (physics, large state diffs) across many rooms on few cores.
- Large in-memory state where garbage-collection pauses hurt tail latency: Discord moved its Read States service from Go to Rust to remove GC spikes at hundreds of thousands of cache updates/s ([Discord](https://discord.com/blog/why-discord-is-switching-from-go-to-rust)); Figma rewrote the performance-critical part of its multiplayer server in Rust for 10x+ serialization speed, keeping Node for networking ([Figma](https://www.figma.com/blog/rust-in-production-at-figma/)).
- Thousands of concurrent rooms per box, where the ~1.3-2.6x per-core edge (section 4) turns into hardware cost.
- You want the same deterministic simulation compiled to WASM for client and server, or a native client (e.g. Bevy).
- You want to learn Rust. That is a fine reason, but a hobby reason, not a performance one. If so, the lowest-risk slice is the room server alone (axum + tokio-tungstenite behind the same JSON protocol) **[est]**; you give up shared TypeScript types unless you generate them.
